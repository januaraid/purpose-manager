## 1. 背景と目的

AIエージェントの作業継続性を、過去のセッション履歴や長期記憶の復元に依存させない。エージェントが「なぜその仕事をするのか」を上位目的から把握できれば、現在の成果物を観測し、必要な作業を自律的に再計画できる。

Purpose Managerは、階層化された目的（Why）と判断原則を、人間とAIハーネスが共有できる形で永続化する軽量な表示・編集ツールである。

### 設計原則

1. **目的を正本とする。** 作業履歴・会話記憶の永続化は本製品の主責務ではない。
2. **上位目的を継承する。** 下位目的は上位目的に貢献する理由を説明でき、上位の判断原則を参照できる。
3. **ハーネスの標準機能を優先する。** Claude Code、Codex、Hermes等の設定や実行方式を変更しない。
4. **YAMLが唯一の正本。** GUI、専用DB、常駐サービスがなくてもファイルの読み書きで運用できる。
5. **再現性と可搬性を優先する。** ファイルはGit等で履歴管理でき、特定ハーネスやPCへロックインしない。
6. **機能を増やさない。** 将来ハーネス標準機能と競合しそうな計画・実行・記憶管理は内製しない。

## 2. スコープと責務

| 領域 | 担当 | 本製品の責務 |
|---|---|---|
| Why（目的・判断原則） | 人間が決定、AIが参照 | YAMLで保存、階層表示、編集、親子関係の検証 |
| What（マイルストーン・成果物） | AIハーネスが立案・編集、人間が結果を確認 | **管理しない** |
| How（手順・タスク・ツール実行） | AIハーネスが選択・実行・自動検証 | **管理しない** |
| セッション履歴・長期記憶 | 各ハーネス | **管理しない** |
| 成果物・実装・テスト | 作業リポジトリ | **管理しない** |

What/Howに関するファイルは各セッションの作業フォルダで作成・管理する。Purpose Managerは形式、ファイル名、マイルストーン管理手法を強制しない。

## 3. 概念モデル

### 3.1 Workspace（ワークスペース）

- Workspaceは、互いに独立した目的ツリーを扱うための**管理単位**であり、目的ノードではない。Workspace自体に目的・親目的・判断原則を定義しない。
- **1 Workspace = 1ローカルフォルダ = 1目的ツリー**を基本とする。Purpose Managerはフォルダを選択・切り替えて複数Workspaceを扱う。
- 各Workspaceの目的IDはそのWorkspace内で一意とする。異なるWorkspace間の親子関係、目的継承、横断参照は認めない。
- Workspace固有の表示名などはWorkspace直下の`workspace.yaml`で保持する。端末ごとのフォルダ選択履歴などはアプリ側のローカル設定に保持する。Workspace設定は目的ノードではなく、目的の継承対象にもならない。
- 会社業務・個人用途など、機密区分や管理主体が異なる目的データは別Workspace／別フォルダで扱う。

### 3.2 Purpose（目的ノード）

- 全ての目的を同じ型のノードで表現する。
- ノードの階層数は可変。会社、事業、プロジェクト、ミッション等は固定のDB階層ではなく、必要に応じて表示上の分類名として扱える。
- 各ノードは固有のIDを持ち、ルート以外は一つの親ノードを参照する（MVPではツリー）。
- 親目的は一つに限定し、複数親や`contributes_to`等の横断的な貢献リンクは設けない。複数の親が必要に見える場合は目的の定義・分割を見直す。
- 子は親の目的と判断原則を読む。継承とは親の文章を子へ複製することではない。
- ノードの固有目的は、親の目的に対してどのように貢献するかを記述する。
- 目的は業務・組織における存在理由や実現したい状態を表す。売上やKPI等の中間目標を企業の最終目的と混同しない。
- 各ノードは任意の`rationale`（目的を設定した背景・理由）を持てる。これは目的そのものではなく、設定時の根拠を説明する情報である。会議履歴・進捗・タスク等の集積場所にはしない。

### 3.3 Session Binding（セッションの対象目的）

- セッションと目的の紐づけは、利用者がハーネス側のプロジェクト設定（例：`CLAUDE.md`）に対象目的への参照を記述する方式を基本とする。
- 同じ目的を複数セッションが参照してよい。
- 同じリポジトリで複数目的を並行して扱える必要があるため、共有ファイルに単一の`active_mission`を固定する方式は標準にしない。
- Purpose Managerは選択した目的について、`CLAUDE.md`等に貼り付けられる短い参照指示を生成・コピーできる。ハーネス固有のセッションIDや実行状態は管理しない。
- 異なる目的を並行運用する場合は、ハーネス側の作業領域・設定・会話中の指定によって対象を区別する。

### 3.4 目的の時間的な有効性

- 目的の階層（親子関係）と時間軸は独立させる。超長期・長期・中期・短期等の固定階層や必須区分は設けない。
- 目的ごとに任意の有効開始日`valid_from`、有効終了日`valid_until`を持てる。未指定は「期間未定」を表し、恒久的な有効性を保証しない。
- 日付は目的の適用期間を示す。`status`は現在の運用上の状態を示し、両者は別々に保持する。期限到来による自動完了・自動アーカイブは行わない。
- 定期的な見直しのため、任意の`review_at`を設定できる。MVPでは通知やスケジューラーを内蔵しない。
- 半期等の切り替えで**目的・価値・判断基準そのものが変わる**場合は新しいIDの目的ノードを作り、旧ノードを保持する。既存IDの目的文を新しい目的で上書きしない。
- **目的が継続し、目標・マイルストーンだけが変わる**場合は新しい目的ノードを作らない。目標の期間管理はハーネス側の責務とする。
- 過去のセッションが参照した目的IDは維持する。過去ノードは原則アーカイブし、削除せず追跡可能にする。
- アーカイブされた目的はGUI上では通常非表示とし、明示的な表示切り替えで閲覧できる。目的IDの直接指定による参照は継続できる。

## 4. ファイルモデル

### 4.1 ファイル配置

一つの目的につき一つのYAMLファイルを作る。各Workspaceは独立した目的用フォルダであり、その中に目的YAML群を置く。作業フォルダのマイルストーンとは分離する。

```text
workspaces/
  work-purposes/           # Workspace: Acme Corp
    workspace.yaml         # Workspace固有設定
    purposes/
      acme-corp.yaml
      acme-jobs.yaml
      job-matching.yaml
  personal-purposes/       # Workspace: Personal Projects
    workspace.yaml
    purposes/
      personal-root.yaml

work-folders/
  job-matching/            # ハーネスの作業領域（管理対象外）
    CLAUDE.md
    ...
```

Workspace内では、目的ID `foo` を必ず `purposes/foo.yaml` に対応させる。**目的IDとファイル名（拡張子を除く）は完全一致**し、同一Workspace内で一意とする。`parent` はファイルパスではなく親目的IDで保持し、`parent: acme-jobs` は `purposes/acme-jobs.yaml` を意味する。ルートの`parent`は`null`。目的ツリーの階層はフォルダ階層ではなく、`parent`関係で定義する。

**目的IDの規則**

- 形式は `^[a-z0-9]+(-[a-z0-9]+)*$`（小文字英数字とハイフン。先頭・末尾・連続のハイフンは不可）、最大64文字。
- 大文字は使わない。Windows・macOSの標準ファイルシステムは大文字と小文字を区別しないため。
- Windowsの予約名（`con` `prn` `aux` `nul` `com1`〜`com9` `lpt1`〜`lpt9`）は使えない。
- GUIは新規作成時に、表示名からIDの候補を自動で入れる（英字を含む表示名はそのまま小文字・ハイフン区切りに、日本語中心の表示名は親ID＋表示名中の英数字＋ランダムな4文字に、既存IDと重なれば `-2` 以降を付ける）。利用者は候補を直接書き換えられる。
- **IDは作成後に変更しない。** 表示名や目的文の修正は編集で行う。目的そのものが変わる場合は新しいIDのノードを作り、旧ノードをアーカイブする（§3.4）。これにより過去セッションの参照先を維持する。

`workspace.yaml`は目的データと分離されたWorkspace設定ファイルとする。MVPでは表示名のみを保持し、将来のWorkspace固有設定の追加余地を残す。

```yaml
# workspace.yaml
name: Acme Corp
```

### 4.2 YAMLスキーマ（MVP案）

```yaml
schema_version: 1
id: acme-jobs
parent: acme-corp # ルートはnull
name: Acme Jobs
purpose: 求職者が自分に合った仕事に出会える状態をつくる。
rationale: > # 任意。なぜこの目的を掲げるかの背景・根拠
  求人情報の量は増えたが、自分に合う仕事を見つけにくい状況は解消されていない。
principles:
  - 求職者を第一に考える
  - 成果に応じて対価を得る
  - シンプルさを保つ
status: active
valid_from: 2026-10-01 # 任意。ISO 8601の日付
valid_until: 2027-03-31 # 任意
review_at: 2027-02-28 # 任意
```

| フィールド | 必須 | 用途 |
|---|---|---|
| `schema_version` | 必須 | 将来のフォーマット移行用 |
| `id` | 必須 | Workspace内で一意。§4.1のID規則に従う。ファイル名は`<id>.yaml`と一致。作成後は変更不可 |
| `parent` | 必須 | 親IDまたは`null` |
| `name` | 必須 | 表示名 |
| `purpose` | 必須 | そのノード固有のWhy |
| `rationale` | 任意 | 目的の設定背景・理由。ノード固有で、原則として継承しない |
| `principles` | 任意 | 判断原則・価値観（配列） |
| `status` | 必須 | `active` / `archived`。目的に達成判定を持たせないため`completed`は設けない |
| `valid_from` | 任意 | 目的が有効になる日（YYYY-MM-DD） |
| `valid_until` | 任意 | 目的が有効な最終日（YYYY-MM-DD、両端を含む） |
| `review_at` | 任意 | 目的の見直し予定日（YYYY-MM-DD） |

期間が指定された場合、`valid_from`が`valid_until`より後にならないことを検証する。日付未指定時には有効・無効を自動推定しない。企業理念など期間を定めない目的ではこれらを省略できる。

### 4.3 背景（`rationale`）の扱い

- `rationale`は**なぜその目的を設定したか**を記述する任意のテキストである。目的（実現したい価値）や判断原則（意思決定基準）と区別する。
- 目的と判断原則は祖先から参照するが、`rationale`は**自動継承・自動注入しない**。必要がある場合に当該祖先ノードのファイルを参照できる。
- 背景の変化だけを理由に目的を自動変更・終了しない。人間が必要に応じて目的の妥当性を再検討する。
- 過去の会話・会議記録、作業履歴、マイルストーン、手段、機密の認証情報を`rationale`へ蓄積しない。

### 4.4 状態と継承

- `status`はノード自身の明示的な状態のみを記録する。`active`は管理対象として有効、`archived`は現在の管理対象から外れた状態を意味する。達成・未達成は表現しない。
- 子目的の**実効状態**は自身と全祖先の状態から計算する。自身と全祖先が`active`のときだけ実効的に有効となる。
- 親をアーカイブすると、その子孫は実効的に非アクティブになる。子孫のYAMLの`status`は自動で書き換えない。
- アーカイブ後も継続すべき子目的は、人間が有効な別の親目的へ付け替える。親変更では単一親・循環禁止を維持する。
- `valid_from`、`valid_until`、`review_at`は`status`と独立し、日付到来を理由に自動アーカイブしない。

### 4.5 親目的の変更

- 親目的の文章や判断原則の変更は、参照時に子孫へ反映される（親の文章を子へ複製しない）。
- 変更に伴う子孫目的の妥当性レビューは推奨するが、レビューの強制や専用UIはMVP対象外とする。

`parent`はIDで保持し、`<Workspace>/purposes/<parent ID>.yaml`へ機械的に解決する。相対パス参照や、目的ファイル群の全文探索を必要としない。Purpose ManagerはIDとファイル名の一致を保存時・読み込み時に検証する。

### 4.6 変更の正本

- GUIとAIは同じYAMLファイルを編集する。
- GUIはファイルの外部変更を再読み込みできる。
- §4.7の検証ルールでエラーとなる内容を検出し、破損した内容を上書きしない。
- 書き込み前には最新内容を照合し、同時変更で他者の修正を黙って消さない。
- Gitによる差分確認・履歴・復元が利用可能。Gitの自動コミットはMVP要件ではない。
- 認証情報や秘密鍵は目的YAMLに保存しない。

**ファイル形式**

- 文字コードはUTF-8（BOMなし）、改行はLF、末尾に改行を入れる。読み込み時はBOMやCRLFも受け付ける。

**GUIでの保存方針**

- 未知のフィールドは削除せず保持する。
- キー順序は既定の順序（`schema_version` `id` `parent` `name` `purpose` `rationale` `principles` `status` `valid_from` `valid_until` `review_at`）に正規化する。未知のフィールドは既定フィールドの後に、元の順序で出力する。
- **YAMLコメントはGUIで保存すると保持されない。** コメントを含むファイルをGUIで保存する場合は、保存前に警告して確認を求める。目的の補足説明はコメントではなく`rationale`に記述することを推奨する。
- 日付は`YYYY-MM-DD`形式のまま保存し、読み書きの往復で形式を変えない。
- 競合検知は、読み込み時に記録したファイル内容のハッシュと保存直前のハッシュを比較して行う。一致しない場合は保存を中断し、再読み込みか差分確認を促す。
- 保存は一時ファイルへの書き込み後に置き換える方式とし、書き込み失敗時に元ファイルを壊さない。

### 4.7 検証ルール

| 区分 | 内容 | 挙動 |
|---|---|---|
| エラー | YAML構文エラー、必須フィールドの欠落、ID規則違反、IDとファイル名の不一致、重複ID、`parent`が文字列でもnullでもない（配列等）、親が存在しない、循環参照、`status`が`active`/`archived`以外（`completed`を含む）、日付がYYYY-MM-DD形式でない、`valid_from` > `valid_until`、未対応の`schema_version` | 該当ファイルは保存しない。GUIでは編集不可として表示する |
| 警告 | Workspace内にルートが複数ある、子の有効期間が親の有効期間の外にはみ出す、`review_at`を過ぎている、コメントを含むファイルをGUIで保存しようとした | 保存できる。GUIに表示する |
| 情報 | 祖先が`archived`のため実効的に非アクティブ、未知のフィールドがある | 表示のみ |

- エラーのファイルがあっても、Workspace全体を読み込み失敗にはしない。正常なノードは表示を続ける。
- 親がエラーで解決できない子は「未解決」グループに表示する。
- 日付は`YYYY-MM-DD`の文字列として検証し、YAMLパーサーの日付型解釈に依存しない。

## 5. 継承とAIへの受け渡し

1. 利用者は目的を選び、Purpose Managerで生成した最小限の参照指示をハーネスの設定ファイル（Claude Codeの場合は`CLAUDE.md`）に貼り付ける。セッションごとの自動紐づけ機能は作らない。
2. ハーネスは指定の目的YAMLを読み、`parent`を `<Workspace>/purposes/<ID>.yaml` で解決してルートまで辿る。
3. ルートから順に目的・判断原則を把握し、現在の目的との整合性を保つ。`rationale`は現在の目的について参照できるが、祖先の背景は必要時だけ読む。
4. 目標設定、計画、タスク分解、実行・検証などのWhat/Howはハーネスに委ねる。
5. 目的の新規作成・変更・削除は人間の承認なしに行わず、目的と目標を混同しない。目的を見失った場合はYAMLを再読する。

### 5.1 CLAUDE.mdへのコピー用テンプレート

以下は生成するテキストの例で、パスは選択中のWorkspaceと目的ファイルから環境に応じて作成する。Purpose Managerは`CLAUDE.md`そのものを自動編集しない。

```markdown
## Purpose

現在の作業目的:
`/path/to/workspace/purposes/job-matching.yaml`

親目的は`parent`のIDに対応する
`<Workspace>/purposes/<ID>.yaml`にあります。

親をルートまで辿り、各階層の目的と判断原則を参照してください。

目的の変更には人間の承認が必要です。
目標設定と実行方法は自由に決定してください。
```

このテンプレートは目的データの解釈・保護に関する最小限の契約のみを記述し、ハーネスの内部ワークフロー、マイルストーンの分解方法、使用モデル、ツール選択を規定しない。複数セッションで目的を変えたい場合の設定方法はハーネス側の責務である。絶対パスは利用端末に依存するため、別端末では参照先を設定し直す。

## 6. 権限・判定ポリシー

| 操作 | 方針 |
|---|---|
| Why本文・判断原則・背景（`rationale`）・親子関係・`status`の変更 | 人間が決定。AIは変更案を提示できる |
| What（マイルストーン）の作成・変更 | AIに委譲 |
| Whatの成果確認 | 人間 |
| Howの実行・結果検証 | AIに委譲 |

AIがYAMLを直接編集することは技術的に妨げないが、目的YAMLの変更は運用ルールで人間の決定に限る。MVPでは専用の承認エンジンを実装しない。目的変更はGit差分やGUIを使って人間が確認する。

## 7. GUIの機能要件

### 必須

1. Workspace（目的用フォルダ）の登録・選択・切り替え。前回選択したWorkspaceを再表示できる。
2. 可変階層の目的ツリー表示（折り畳み・展開）。
3. 目的の新規作成・編集・アーカイブ。物理削除は子を持たないノードに限り、確認のうえで行う（§10）。アーカイブ済みは通常非表示とし、表示切り替え・ID指定で閲覧可能。
4. 親ノードの選択・変更。
5. 目的・背景（任意）・判断原則・状態の編集。
6. 目的ごとの有効期間・見直し予定日の任意表示・編集。期間未設定のノードも扱える。
7. 現在選択中の目的について、祖先の目的・原則を参照できる表示。
8. YAMLの検証（§4.7のエラー・警告・情報の区別）、エラー通知、外部変更の反映。
9. 選択目的のファイルパスおよび親ID解決規則を含む、`CLAUDE.md`向け参照指示をコピーできること（ハーネス設定ファイルの自動変更はしない）。

### MVP対象外

- エージェントの起動・スケジューリング・監視。
- マイルストーン・タスク・進捗ボード。
- セッション履歴の取り込み・検索・要約。
- MCPサーバー、LLM Proxy、専用ベクトルDB。
- 成果物の自動判定、記憶抽出、目的への自動昇格。
- 組織向けロール管理やクラウド同期。
- YAMLコメントの保持。

## 8. 非機能要件

- ローカルファースト。目的の閲覧・編集にネットワーク接続を必須としない。
- GUI停止中もAIが目的YAMLを直接読める。Workspace切り替えはファイルの移動・複製を伴わない。
- Windows 11とmacOSを初期対象とする。GUI技術の暫定選定はTauri 2 + Svelte + TypeScript + Rust。YAMLデータ自体はOS非依存。
- 特定のClaude Codeバージョン、モデル、MCP、Hook、Proxyへ依存しない。
- 元ファイルを壊さない保存、入力検証、復元可能な変更履歴を優先する。
- 目的情報の機密区分と保存場所は利用組織のルールに従う。

## 9. 受け入れ条件

1. 親子関係を持つ5階層以上の目的をYAMLだけで表現・表示できる。
2. 子ノードから親を辿り、祖先の目的・原則を確認できる。
3. 同じ目的を別のClaude Codeセッションから参照しても、目的のコピーが発生しない。
4. 異なる目的を同時並行のセッションへ指定できる。
5. GUIを終了しても、AIがYAMLの読み取り・編集を継続できる。
6. GUIと外部エディタ双方の変更が反映され、競合時に黙って上書きされない。
7. 重複ID、IDとファイル名の不一致、親欠落、循環参照、YAML構文エラーを検出できる。
8. 目的ツリー表示・編集のためにハーネスの特殊設定やLLM APIへの中継を必要としない。
9. 期限なしの長期目的と、日付付きの半期目的を同一ツリー内で管理できる。
10. 期間の不整合を検知でき、期限を迎えても`status`が自動変更されない。
11. 半期交代時に新旧目的を別IDで保持し、過去セッションの参照先を維持できる。
12. 親が`archived`、子が`active`の場合も子の実効状態は非アクティブとして計算し、元のYAMLを変更しない。
13. `completed`を状態として受け付けず、アーカイブ済み目的を表示切り替えとID指定で参照できる。
14. `rationale`を省略しても有効なYAMLとして読み書きでき、指定時にはGUIで編集・表示できる。祖先の`rationale`は自動継承しない。
15. 複数Workspaceをフォルダ単位で登録・切り替えでき、切り替え操作によって目的ファイルが変更・複製されない。
16. 異なるWorkspaceに同じ目的IDが存在しても衝突せず、Workspaceをまたぐ`parent`参照は解決しない。
17. `parent: acme-jobs`が同一Workspaceの`purposes/acme-jobs.yaml`に解決され、ファイル名と目的IDが不一致なら検証エラーとなる。
18. 選択目的から`CLAUDE.md`向け指示をコピーでき、ハーネスが標準のファイル読み取り機能で祖先目的を辿れる。
19. `workspace.yaml`の`name`をWorkspaceの表示名として読み込み、目的YAMLや他のWorkspaceに影響しない。
20. ID規則違反（大文字、予約名、使えない文字、64文字超）を検出できる。
21. GUIで1フィールドを編集して保存しても、他のフィールドの値と未知のフィールドが保持され、キーが既定の順序で出力される。コメントを含むファイルの保存時には事前に警告される。
22. 一部のYAMLが壊れていても、他の目的ノードは表示・編集できる。
23. Windowsで保存したファイルをmacOSで読んでも差分が出ない（文字コード・改行が統一されている）。

## 11. 将来拡張の判断基準

追加機能は「ハーネスが標準で担うべき機能か」「GUIがなくなっても継続利用できるか」「新しいPCで再現できるか」を評価してから導入する。MVPで不要な自動化を先取りしない。
