## 1. 開発の目的と原則

### 目標
- 目的（Why）の階層・判断原則・背景・時間情報を、ローカルYAMLを唯一の正本として扱えるGUIを提供する。
- 個人のWindows 11と、利用が承認された職場のmacOS環境で使用できる。
- 開発物をGitHub Publicリポジトリに公開し、GitHub Releasesから配布可能にする。
- Claude CodeをはじめとするハーネスはYAMLを直接読み取る。Purpose Managerはハーネスの実行管理を担当しない。

### 開発原則
1. **MVP優先:** 既存仕様書の受け入れ条件を満たすまで新機能を増やさない。
2. **ローカルファースト:** 利用にクラウド、専用DB、常駐サーバー、ログインを要求しない。
3. **データ可搬性:** アプリが壊れてもYAMLを直接編集・参照できる。
4. **疎結合:** Claude Code、Codex、Hermes等の内部API、Hook、Proxyに依存しない。
5. **安全性:** ファイル破損・競合によるデータ消失を防ぎ、会社データと公開ソースを分離する。
6. **再現性:** 新しいPCでリポジトリからビルドでき、配布済みバイナリからも導入できる。

## 2. 技術スタック

| 領域 | 選定 | 備考 |
|---|---|---|
| デスクトップ実行基盤 | Tauri 2 | Windows / macOS。ネイティブのファイル操作を担当 |
| UI | Svelte + TypeScript | 階層ツリー、編集パネル、Workspace切替 |
| スタイル | CSS（必要に応じてTailwind CSS） | MVPの依存を増やさない。UI実装時に選択 |
| ローカル処理 | Rust | YAML入出力、構造検証、安全な保存、ファイル監視 |
| データ | YAML | `workspace.yaml` + `purposes/<ID>.yaml`。独自DBなし |
| 品質管理 | Rustテスト、TypeScriptテスト、E2E/手動テスト | ドメインテストを最優先 |
| ソース管理 | Git / GitHub Public | コードと架空のサンプルデータのみ公開 |
| CI/CD | GitHub Actions | lint/test/build、タグによるRelease作成 |
| 配布 | GitHub Releases | Windows向けインストーラー、macOS向けパッケージ |

**設計上の判断:** UIとファイル操作の境界を分離する。将来のWeb版を考慮してよいが、Web版を同時開発しない。YAMLの解析・検証・保存はRust側に集約し、TypeScript側ではYAMLをパースしない（解釈の二重化を避ける）。保存時は未知フィールドを保持し、キー順序を既定順に正規化する。YAMLコメントは保持しない（仕様書§4.6）。

## 3. リポジトリ構成（案）

```text
purpose-manager/
  src/                    # Svelte / TypeScript UI
  src/lib/                # UIモデル、画面用ロジック
  src-tauri/              # Rustドメイン処理、Tauri設定
  tests/                  # サンプルWorkspaceによる検証
  fixtures/
    sample-workspace/
      workspace.yaml
      purposes/
        company.yaml
        project.yaml
  .github/workflows/      # CI / release
  docs/
    specification.md      # 製品仕様書（公開用。例が架空データであることを確認してから配置）
    development-plan.md   # 本書
  .gitattributes          # *.yaml / *.md を text eol=lf に固定
  README.md
  LICENSE
```

**注意:** 実際の会社のPurpose YAML、非公開組織情報、認証情報、社内ファイルパス、業務成果物はPublicリポジトリに含めない。`fixtures`は架空のデータのみ。

## 4. 実装フェーズと完了条件

### Phase 0 — 開発環境・骨格

- Tauri 2 + Svelte + TypeScript + Rustの最小アプリを作成する。
- Windowsで起動できることを確認する。早期にmacOSでも起動を確認する。
- GitHub Publicリポジトリを作成し、`.gitignore`、README、ライセンス候補、CIの雛形を配置する。
- UIとRustロジックを明確に分ける。

**完了条件:** クリーン環境でREADMEの手順どおりにビルドでき、サンプル画面が起動する。

### Phase 1 — YAMLと目的ツリー（GUIなしでもテスト可能）

- Workspaceの読み込み・切替。`workspace.yaml`の表示名を取得。
- `purposes/<ID>.yaml`の列挙、読み込み、編集、保存。
- 仕様書§4.7の検証ルールを実装する。エラー・警告・情報を区別し、一部のファイルが壊れていても他のノードを読み込めるようにする。
- ID規則（形式、64文字以内、Windows予約名の禁止）、IDとファイル名一致、重複ID、親欠落、複数親禁止、循環参照、同一Workspace内参照を検証。
- 親の`archived`を反映する実効状態の算出。`completed`は禁止。
- `purpose`、`principles`、`rationale`、日付属性の読み書き。日付は`YYYY-MM-DD`文字列のまま往復させる。
- 未知のフィールドを保持し、キーを既定順で出力する。ファイルにコメントが含まれるかを検出する（GUIの保存前警告に使う）。書き換えによる差分をテストする。
- 文字コードUTF-8（BOMなし）・LF・末尾改行で保存する。BOM・CRLFの読み込みも受け付ける。
- 読み込み時のハッシュと保存直前のハッシュによる競合検知、一時ファイル経由の安全な保存、失敗時の元ファイル保護。
- 自分の保存で発生したファイル監視イベントを外部変更と誤判定しない（保存した内容のハッシュと一致するイベントは無視する）。

**完了条件:** 仕様書のデータ・継承・時間・保存に関する受け入れ条件を自動テストで確認できる。

### Phase 2 — 表示・編集GUI

- Workspaceの登録・選択・切替。
- グラフィカルな目的ツリーの表示、折り畳み、選択、アーカイブ表示切替。
- ノード詳細の編集（目的、背景、原則、親、状態、日付）。
- 親変更時には継承元の変更と影響範囲を表示する。循環・親欠落を防ぐ。
- ファイル外部変更の反映。編集中の変更競合では自動上書きしない。
- 親がアーカイブされた子孫の実効状態を、元YAMLの状態と区別して表示する。
- コメントを含むファイルを保存する前に、コメントが失われることを警告して確認を求める。
- 物理削除は子を持たないノードに限る。確認ダイアログで過去セッションの参照先が失われることを示す。
- 検証のエラー・警告・情報を区別して表示する。親を解決できないノードは「未解決」グループに出す。

**完了条件:** YAMLを直接開かなくても、複数階層の目的を理解・編集できる。外部エディタと併用してもデータを失わない。

### Phase 3 — ハーネスとの接続（最小）

- 選択中のPurposeについて、`CLAUDE.md`向け参照指示をコピーできるようにする。
- 指示には実ファイルパス、`parent`のID解決方法、祖先目的と判断原則の参照、目的変更時の人間承認のみを含む。
- `CLAUDE.md`の自動書換え、Claude Codeの自動起動、セッションAPI統合は行わない。
- 実際にClaude Codeで`parent`をルートまで辿り、祖先の目的と原則を理解できるか確認する。

**完了条件:** 標準のClaude Code環境で、コピーした指示だけで目的階層を解決できる。GUIが閉じていても同じYAMLを参照できる。

### Phase 4 — クロスプラットフォーム検証・公開

- Windows 11とmacOSでファイル操作、パス解決、GUI、エラー表示をテスト。
- macOS Apple Siliconを優先。Intel macOS対応は必要な利用者・環境に応じて追加判断。
- GitHub Actionsでテスト・ビルドを実施。バージョンタグからGitHub Releasesへ成果物を添付。
- READMEに導入方法、Workspaceサンプル、ハーネス連携方法、既知の制約を記載。
- Release前に秘密情報・会社固有情報の混入、依存ライセンス、成果物の動作確認を実施。

**完了条件:** GitHub Releasesから入手したアプリが、許可されたWindows/macOS環境で起動・利用できる。

## 5. GitHub公開・配布設計

### 5.1 ブランチとバージョン
- `main`を常にビルド可能な状態に保つ。
- 機能変更は小さなPull Requestで取り込み、CIでテストする。
- `v0.1.0`等のGitタグをReleaseの単位にする（例示）。
- MVPでは自動更新機能を持たず、利用者がGitHub Releasesから手動更新する。

### 5.2 CI/CD
- **PR / main:** Rustのフォーマット・静的解析・テスト、TypeScriptのチェック・テスト、ビルド確認。
- **Version tag:** Windows/macOS向けのビルド成果物を生成し、GitHub Releasesに登録。
- GitHub Actionsの権限は必要最小限とし、依存アクションのバージョン固定・秘密情報管理を実施。
- macOSの署名・公証が必要になったら、Apple Developer Programの要件と証明書管理を別途整備。未署名配布を前提に職場Macでの実行を保証しない。

### 5.3 ライセンスと公開範囲
- コードの公開ライセンスは**MIT**とする（2026-11-02 決定）。会社の副業／成果物規程との関係は利用者が確認する。
- README、CONTRIBUTING、SECURITY等は配布の規模に応じて追加。最初から重い運営体制は作らない。
- 公開するのはコード・ドキュメント・架空のサンプルWorkspace。業務用Workspaceは含めない。

## 6. 職場Macへの導入・利用

### 6.1 事前確認
1. 会社の端末管理・セキュリティポリシー上、個人開発の外部アプリ／GitHub Releases由来の実行ファイルの導入が認められるか確認する。
2. 未署名アプリや公証のないアプリの実行に制限があるか確認する。会社の管理制限を回避しない。
3. 職場でGitHubへアクセスできるか、承認済みのソフトウェア導入ルートがあるか確認する。
4. 社内の目的情報をどこに保存できるか、外部サービスへの送信禁止・端末保護要件を確認する。

### 6.2 導入
- 会社が許可する方法でGitHub ReleasesのmacOS版を取得し、必要に応じてIT管理者の承認を受ける。
- ダウンロード元のReleaseとバージョンを確認する。公開バイナリが許可されない場合は、承認されたビルド・配布ルートを使う。
- 業務用Workspaceは会社が許可するローカル／社内管理ストレージに置き、個人用Workspaceと分離する。
- サンプルデータで読み書き・ファイル監視・ハーネスからの参照を検証してから実データを扱う。

### 6.3 職場利用に関する安全原則
- Purpose Managerにクラウド送信や解析SDKをMVPで組み込まない。
- 会社の情報を個人GitHub Publicリポジトリ、Issue、Actionsのログ、サンプルファイルへ貼り付けない。
- GitHub Public公開はソフトウェアの公開であり、業務データの公開を意味しない。
- データの保管・バックアップはWorkspaceを管理する利用者／組織の方針に従う。

## 7. テストの優先順位

| 優先 | 項目 | 代表的な確認 |
|---|---|---|
| P0 | データ保護 | 書き込み失敗、競合、YAML破損時に元データを失わない |
| P0 | 階層整合性 | 親解決、単一親、循環なし、ルートからの継承 |
| P0 | クロスOS | Windows/macOSで同一Workspaceを正しく読める |
| P1 | UI操作 | ツリー俯瞰、親の変更、アーカイブ、背景編集 |
| P1 | ハーネス連携 | `CLAUDE.md`指示で目的を辿れる |
| P1 | 公開配布 | Release成果物から起動・編集できる |
| P2 | 長期運用 | 大きな目的ツリーの表示性能、復元性、使い勝手 |

## 8. MVPに含めないもの

- AIレビュー、LLM API連携、MCP/Proxy、Hookの導入。
- セッション自動取得・起動・監視、目標やタスクの管理。
- リアルタイム共同編集、クラウド同期、組織アカウント、権限管理。
- 過去の特定日時の目的ツリー復元、目的のバージョン管理。
- 3Dビュー、HTML-in-Canvas、タイムラインの高度な可視化。
- 自動アップデート、テレメトリー。

## 9. 実装前に確定する最小事項

以下は作業を止めるほどの未決事項ではなく、Phase 0〜2の実装時に選択する。

- RustのYAMLライブラリの選定（`serde_yaml`はメンテナンスが終了しているため、後継の候補を比較する）。選定条件は、未知フィールドの保持、キー順序の制御、日付を文字列のまま扱えること、コメントの有無を検出できること。
- Workspaceのローカルパス記憶方法、OSのファイル選択・権限モデル。
- 表示ツリーのレイアウトライブラリとノード編集パネルの細部。
- 物理削除の扱い（初期はアーカイブ中心を推奨）。
- リリースに必要な署名・公証の実施時期と、会社PCでの利用可否。
